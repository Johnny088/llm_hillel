# Контрольна точка фінального проєкту

## Варіант 1. Асистент первинного аналізу інцидентів

- Проблема: необроблені повідомлення про помилки надходять у різних форматах і потребують ручного сортування.
- Цільовий користувач: черговий backend-розробник або support engineer.
- Очікуваний результат агента: структурований опис симптомів, компонентів, часових позначок, рівня пріоритету та наступних діагностичних кроків.
- Можливі джерела даних: синтетичні tickets, відкриті приклади логів, внутрішня документація без секретів.
- Потенційні ризики: витік токенів або персональних даних із логів, prompt injection у ticket, хибний рівень пріоритету.

## Варіант 2. Аналізатор навчальних матеріалів

- Проблема: великі відкриті навчальні тексти складно швидко перетворити на контрольований конспект і перелік термінів.
- Цільовий користувач: викладач або автор технічного курсу.
- Очікуваний результат агента: типізований конспект, ключові терміни, прогалини у визначеннях і чернетка контрольних запитань.
- Можливі джерела даних: власні матеріали, відкриті документації, тексти з сумісною ліцензією.
- Потенційні ризики: порушення авторських прав, втрата контексту під час скорочення, вигадані твердження.

## Варіант 3. Екстрактор вимог із проєктного брифу

- Проблема: вимоги, обмеження та критерії приймання розпорошені в неструктурованому брифі.
- Цільовий користувач: junior developer або tech lead невеликої команди.
- Очікуваний результат агента: структурований перелік функціональних вимог, обмежень, відкритих питань і Definition of Done.
- Можливі джерела даних: синтетичні брифи, відкриті технічні завдання, шаблони user stories.
- Потенційні ризики: пропущені неоднозначності, помилкова інтерпретація пріоритетів, передавання конфіденційних деталей зовнішньому API.
